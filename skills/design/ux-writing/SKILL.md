# 界面文案

写功能时顺手写下的界面文字，常常用的是写代码时脑子里的词：代码里给东西起的名字、程序正在做的动作、只有正看着这段代码的人才知道指什么的「这个」「它」。写的人手里有代码，读着总是通顺；用的人手里只有这句话和它所在的位置。只记着「不要有程序味」拦不住，因为写的那一刻注意力在代码上，认不出眼前这句就是原则说的那种。

所以这里的做法是换个位置读：写之前先把要写的字单独列出来，对着页面上现成的文案写；写完从代码里取出原文，逐条回到它出现的地方看；再请一个没看过代码的读者复述一遍，看他理解得对不对。

`<skill-dir>` 指本 SKILL.md 所在的目录，调用脚本时换成绝对路径。

## 做什么、查多大范围

两件事：

- **写**：做带界面文字的功能时，动手前按「写的时候」一节列清单，写完接着做「交付前检查」。
- **检查**：按「交付前检查」一节的步骤做。写完接着做，也可以单独被要求检查。

检查多大范围，按用户说的定；没说就查这次改动：

| 用户说的 | 查的范围 | 怎么取文案 |
|---|---|---|
| 没说范围（做功能时，或「检查这次改动的文案」） | 还没提交的改动 | `changed_copy.py` |
| 某几次提交 | 那几次提交之间的改动 | `changed_copy.py --range A..B` |
| 某个页面、模块或文件 | 这些文件里的全部文字 | `changed_copy.py --all 路径…` |
| 整个项目 | 全部文字，按页面分批，见「整个项目走查」 | 每批 `--all 这一批的路径` |

只说了页面或模块名、没给文件时，先在代码里找到对应的文件，汇报里写明查了哪些文件。

适用范围：以简体中文界面为主。英文界面可以用九类问题、复述测试和脚本，`conventions.md` 不适用。其他语言没有验证过，九类问题可以参考，口气和用词要另找依据。

## 先弄清读者

写和检查都从这里开始，一次会话做一次。只读项目里本来就有的东西：规则文件（AGENTS.md、CLAUDE.md 这类）、设计或界面规范文档、多语言文案表、现有的界面文案（挑十来条写得好的读）。从中归纳三件事：

1. **读者是谁**：普通消费者、某个行业的业务人员，还是开发者。这决定哪些词算看不懂：开发者工具里的 SSH 公钥、CNAME 记录是读者自己的词，换成白话反而认不出。
2. **东西在界面上叫什么**：页面上反复出现的对象和操作，现有文案怎么称呼。代码里往往是另一套叫法，不先查清就会把那一套写上界面。用户能改的名字（昵称、自定义名称）从数据里取，不写死。
3. **口气**：称呼用「你」还是「您」，偏口语还是偏正式。

依据冲突时按这个顺序：用户这次的指令 > 项目成文的规范 > 项目现有文案里的多数写法 > `<skill-dir>/references/conventions.md`。项目里找不到依据的项（比如称呼、报错句式）才看 `conventions.md`。读者是儿童、老人，或产品属于金融、医疗、政务这类严肃场景时，口气以读者为准，`conventions.md` 里的默认（比如「用你不用您」）让位。

项目里两种口气并存时，跟着这次改动所在页面的写法走，不顺手统一，把并存的情况作为发现写进汇报。归纳出的结论用一两句话写进汇报，让用户一眼看出方向对不对。

## 九类问题

前五类多出在写的时候，第 6 类多出在回头改的时候，后三类两头都会出。用户说的「程序味」多落在第 1、2、3 类，「AI 味」多落在第 4、6、7 类。

第 1、2、3 类认出来就归必改，不因为「读得懂」降级：用户能猜懂一句程序的说法，不等于该让他去猜。读者是企业员工、后台操作人员时也一样，他们同样是用户；只有读者自己行业里的词（开发者工具里的 SSH 公钥）不算第 1 类。

写的时候用下面这张表就够；检查时，或者拿不准时，读 `<skill-dir>/references/checklist.md`，里面有每类的例子和「不算问题」的边界。

| 类 | 怎么认 |
|---|---|
| 1. 用了做的人才懂的词 | 用户嘴里会说这个词吗？界面上没解释过，他第一次看能懂吗？接口返回的错误原文、错误码显示到界面上也算（有意设计的除外，见交付前检查第 5 步） |
| 2. 指代悬空 | 把这句单独拿出来读，「这个」「那次」「它」指什么？ |
| 3. 讲程序在做什么 | 这句在回答「程序在干嘛」，还是「我怎么样了、我能干嘛」？ |
| 4. 替用户猜原因，或说了不真实的话 | 回到代码看：程序真的知道这个原因吗？这句承诺做得到吗？ |
| 5. 生造的口语 | 印在成熟产品的界面上会显得随便吗？去掉上下文别人听得懂吗？ |
| 6. 公文腔和改过头 | 是大家手机上天天见的说法吗？改后是不是更长、更绕、更像文件？ |
| 7. 塞太多、重复或空话 | 遮住这句，用户会少知道什么？ |
| 8. 不看放在哪 | 按钮、徽标放得下吗？报错、提示条、空状态给了下一步吗？ |
| 9. 同一个东西几种叫法 | 在项目里搜这个词和它的近义词，别处怎么叫？ |

动手改任何一条之前再过一关：**这是用户会读不懂、读错、被误导，还是只是我会换个写法？** 后者不改。确实属于第 1、2、3 类的，不算「换个写法」。多数文案本来就是好的；改得越多，用户要核对的越多，改错意思的机会也越多。法务、监管要求的固定文案只指出，不改。

## 写的时候

写功能时注意力在代码上，字是顺手带出来的。先把字单独拿出来，才有机会像读者那样看它们。

1. **动手写代码之前，先在回复里列出这次要新增或修改的界面文字。** 每条写三样：出现在哪个页面的哪个元素；照着哪一条现成文案写（同页面或相邻页面里的同类文字，比如同一种按钮、同一种报错）；拟写的文字。照着现成的写，叫法和句式自然和产品一致。
2. **用上面的九类表把清单过一遍**，有问题的先在清单里改掉。
3. **全新的概念没有现成文案可照时**，给它起的名字单独列出：有人可问就问；没人可问就先用一个容易撤回的默认（贴近用户的说法、不和已有叫法撞车），在汇报里写明。
4. **写完做一遍交付前检查。** 清单里的字写进代码时常会变样，还会多出写着写着才加的提示和报错，这一遍查的就是这些。新文字在对照表里「改前」填「（新增）」。

## 交付前检查

回头看文案有自己的坑：凭印象列出代码里没有的文案、把正常的词也改掉、把意思改错。下面的顺序就是冲着这些坑排的。

### 1. 从代码里取出文案

不凭记忆列，用脚本取：

```bash
python3 <skill-dir>/scripts/changed_copy.py                  # 工作区相对 HEAD 的改动，含未跟踪的新文件
python3 <skill-dir>/scripts/changed_copy.py --range A..B     # 两个提交之间
python3 <skill-dir>/scripts/changed_copy.py --all src/       # 整个项目走查，可给多个路径
```

英文界面或中英混排的文案表加 `--ascii`；在别的目录跑加 `-C 目录`；要结构化输出加 `--json`。脚本扫常见的前端和移动端源码，以及 strings.xml、.strings、.xcstrings、.arb、.po、.properties 这类集中存放文案的文件；项目用了别的扩展名，用 `--ext .foo,.bar` 补上。输出带文件和行号，文案表带键名，改动模式下还列出同一处删掉的旧文字。

脚本只做提取，会多也会漏，取出来后自己过一遍：

- 去掉用户看不到的：日志、写给模型的提示词、测试数据、只在开发者模式里出现的内容。
- 补上取不到的：拼接出来的句子、接口返回后原样显示的文字、写在配置或数据里的文字。
- 「留意」一栏只是提醒多看一眼，其中「对照现有口气」只说明这里的口气可能和项目其他地方不同。命中的可能没问题，没命中的也可能有问题。

### 2. 每条回到现场

对每一条，读它所在的代码，弄清四件事：

- **在哪**：哪个页面的哪个位置，用界面上的说法描述，不写文件路径。
- **是什么**：按钮、徽标、标题、提示条、确认框、空状态、悬停提示、权限说明、推送，还是成段的说明。
- **什么情况下出现**：用户刚做了什么，看到后能做什么。
- **旁边还有什么字**：同一组的其他选项、上方的标题、已经显示出来的信息。

同一句话放在徽标里和放在确认框里，标准完全不同；不知道代码在什么情况下显示这句，改出来的意思就可能是错的。

### 3. 对照九类问题

读 `<skill-dir>/references/checklist.md` 和 `<skill-dir>/references/conventions.md`。第 4、6、8、9 类要看代码和别的页面才能判断，由你自己答：程序是否真知道这个原因、改动是不是改过头、位置和宽度合不合适、别处怎么叫。

### 4. 复述测试

写的人读自己的文字总觉得通顺，所以要找一个没看过代码的读者。读 `<skill-dir>/references/retell.md`，按里面的格式准备清单，连同其中给读者的说明原样交给一个子代理。复述说错了、或读不出意思的才算问题；说对了但标了「不顺」的，归入可改可不改。第 1、2、3、7 类主要靠这一步发现；读者对口气的感受只作参考。

派不了子代理时，自己按同样的输入做一遍，在汇报里注明「由写的人自查，可信度低」。这次只动了标准词（保存、取消、删除这类）或只改了标点时可以不做，汇报里写明跳过了。

### 5. 分级

第 3、4 步标出来的条目，先过「改之前那一关」，再分级：

- **必改**：用户会看不懂、理解错、被误导；第 1、2、3 类的问题，哪怕读得懂；说的和程序实际做的不一样；出了错不告诉用户能做什么；界面上显示了接口返回的错误原文或错误码（有意设计的除外）。直接改。
- **可改可不改**：读得懂，只是不够顺、口气可以更好、标点不统一（第 1、2、3 类不在这里）。默认不动，汇报里一句话说有多少条、什么类型。
- **改名**：功能名、状态名、列名、分类名（比如失败原因的名称）这类用户已经认熟的叫法。不直接改，列进「拿不准」给候选：改名会牵动别的页面、帮助文档和用户的习惯。这类叫法就算属于第 1、2、3 类，也按改名处理，不按必改直接改。

改的时候守住两点：意思不变，原文说的是现象，就不要改成你从代码里读出来的原因；同一个词别处也在用的，要改就一起改，并列出连带改动。

有两种情况，只改字改不好，要动几行代码：

- **话说得含糊，但代码手边就有能说具体的信息。** 有些提示要覆盖好几种情况，只好说得笼统，比如「上传失败」「操作失败」。先看显示这句话的那段代码手边有没有现成的数据能分清是哪种情况：接口返回的错误码、刚刷新回来的数据里这条记录的当前状态、用户刚选的文件或刚填的内容。有的话，按情况各写一句具体的话，用这些数据挑一句显示；分不清时仍显示原句。比如上传附件失败时一律显示「上传失败」，而代码里已经拿到了文件大小、也知道上限是 20MB，就在超过上限时显示「文件超过 20MB，请压缩后再上传」，其他情况仍是「上传失败，请重试」。要拿到这些信息得新发一次请求，或者得改按钮、改操作步骤才能说清时，不改代码，在汇报里写出建议。
- **界面上显示了接口返回的错误原文或错误码。** 原文是写给程序员看的，常是英文、带编号和字段名；错误码不管是数字还是 `PERMISSION_DENIED` 这类英文名，用户多半看不懂、用不上。默认不显示：这次改动里的代码把它们显示给用户的，不管是直接显示，还是经过项目里共用的取错误文字函数原样带出来，都在这次改动的代码里换成自己写的话，说清发生了什么、能做什么：认识的错误码各写一句，不认识的用一句通用的报错。有意设计的展示照项目做法保留，但要有看得见的依据：项目规范或产品文档要求显示；用户这次指令要求；或者项目专门做了放它的地方，比如可复制的「错误码 / 参考编号」区域、排障用的折叠区（要把编号报给客服、银行或 IT 的产品常这样做）。保留的编号只能跟在人话后面，不能代替人话；项目做好的这类区域不删，也不改它显示什么，在汇报里写明它会露出原文，交给用户定。只是通用报错模板顺手拼上了错误码、没有别的依据的，不算有意设计：这次改动用到它的地方换成不带码的说法。共用函数全项目都在用，改它会影响所有页面，不动它，在汇报里指出。

### 6. 改代码，然后汇报

改完**重新跑一次脚本**，按新的输出写对照表，保证每一行都对得上真实改动：

| 位置 | 改前 | 改后 | 原因 |
|---|---|---|---|
| 问诊页 · 发出消息后的状态（示意） | 消息已入队，等待对端响应 | 已发送，等待医生回复 | 「入队」「对端」是程序的说法，用户想知道的是在等谁 |

- 「位置」写界面上的位置；新写的文字「改前」填「（新增）」，让用户看到这次多了哪些字。
- 「原因」一句话说这句对用户哪里不好，不写「优化表达」这类空话。
- 只改了标点或空格的不进表，合成一句话说明。

汇报按下面的顺序写。要用户做决定的放在对照表前面：对照表常有几十行，放在后面的待定项容易被漏看。

1. **一句话结论**：改了多少处、在哪几个文件、有没有提交；再用一句话写读者和口气的结论，方便用户一眼看出方向对不对。
2. **拿不准**：每条给两三个候选和你倾向哪个。起名、定叫法、涉及口气的多半在这里。没人可问时先用的默认也列在这里，写明怎么撤回。
3. **对照表**：条目多时按页面分组，每组一个小标题。
4. **没验证的**：只读了代码、没在页面上看过的，如实说：会不会撑破按钮、会不会被截断，要看了页面才知道。
5. **过程信息**：项目里口气并存的情况；看了多少条、改了多少条、多少条属于可改可不改没动；复述标记了但没采纳的条目和原因。

## 整个项目走查

按页面或功能分批，每批从取文案走到汇报，再做下一批；不要先把整个项目读完再凭印象改。有人可问时，第一批做完先给用户看对照表，确认方向再继续：方向没对齐就批量改，返工量很大。没人可问时按默认做完，把待定项连同用了的默认写进汇报，方便用户一次撤回。

分批交给子代理时，把读者和口气的结论、`checklist.md` 和 `conventions.md` 的路径、这一批的文件范围写进说明，要求交回的每一行带文件和行号；收回后用脚本输出核对，对不上的整份退回重做。

## 退路

- **不是 git 仓库，或没有 python3**：脚本用不了。逐个读这次动过的文件，把界面文字抄成清单，每一条都要是代码里的原文。
- **文案来自后端、CMS 或配置平台**，不在仓库里：指出来，请用户给出原文和出现的位置；拿不到就在汇报里列为没查到的部分。
- **多语言文案表**：只改源语言，键名和占位符（`{count}`、`%s` 这类）原样保留；其他语言只指出需要跟着改，不动。

## 不做的事

- 不替用户定叫法和口气：会牵动别的页面和用户的习惯，给候选让用户定。
- 不改项目的规则文件和规范文档：那是项目的决定。
- 不提交：用户要先看对照表。
- 不保证文字放得下：要看了页面才知道，没看过就如实说。
