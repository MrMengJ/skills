# 界面文案

写功能时顺手写下的界面文字，常常用的是写代码时脑子里的词：代码里给东西起的名字、程序正在做的动作、只有正看着这段代码的人才知道指什么的「这个」「它」。写的人手里有代码，读着总是通顺；用的人手里只有这句话和它所在的位置。只记着「不要有程序味」拦不住，因为写的那一刻注意力在代码上，认不出眼前这句就是原则说的那种。

所以这里的做法是换个位置读：写之前先把要写的字单独列出来，对着页面上现成的文案写；写完从代码里取出原文，逐条回到它出现的地方看；再请一个没看过代码的读者复述一遍，看他理解得对不对。

`<skill-dir>` 指本 SKILL.md 所在的目录，调用脚本时换成绝对路径。

## 做什么、查多大范围

两件事，用同一套判断（见「怎么判断一句话」），区别只在拿到句子的时机：

- **写**：做带界面文字的功能时，先有句子再写代码。动手前按「写的时候」一节列清单，写完接着做「交付前检查」。
- **检查**：代码已经写好，把句子取出来看。按「交付前检查」一节的步骤做。写完接着做，也可以单独被要求检查。

检查多大范围，按用户说的定；没说就查这个分支上的改动：

| 用户说的 | 查的范围 | 怎么取文案 |
|---|---|---|
| 没说范围（做功能时，或「检查这次改动的文案」） | 当前分支从主干分出来以后的提交，加上还没提交的改动 | `changed_copy.py --branch` |
| 只查还没提交的 | 还没提交的改动 | `changed_copy.py` |
| 某几次提交 | 那几次提交之间的改动 | `changed_copy.py --range A..B` |
| 某个页面、模块或文件 | 这些文件里的全部文字 | `changed_copy.py --all 路径…` |
| 整个项目 | 全部文字 | 按「范围大时分批」，每批 `--all 这一批的路径` |

没说范围时查分支，是因为一个分支通常就是一件事，分支上已经提交的文字也是这件事写的。在主干本身上没有「分支自己的提交」，只取到还没提交的；脚本找不到主干时也只取还没提交的，并且会打出一行说明，照实写进汇报。同一个分支第二次检查时，上次查过的会再查一遍：可改可不改的默认不动，`decisions.md` 里拍板过的不再问，多出来的主要是时间。

只说了页面或模块名、没给文件时，先在代码里找到对应的文件，汇报里写明查了哪些文件。不管哪种范围，取出来超过一两百条，按「范围大时分批」做。

适用范围：以简体中文界面为主。英文界面可以用九类问题、复述测试和脚本，`conventions.md` 不适用。其他语言没有验证过，九类问题可以参考，口气和用词要另找依据。

## 先弄清这个产品

写和检查都从这里开始，一次会话做一次。

先看项目根目录有没有 `.ux-writing/decisions.md`：里面是用户拍板过的叫法和写法，有就直接用，做法见下一节。然后回答三个问题：

1. **产品是做什么的、给谁用**：一两句，比如「家长给孩子用的英语练习 App」。这决定口气的分寸：给儿童、老人用，或属于金融、医疗、政务这类严肃场景时，口气跟着这些用户走，`conventions.md` 里的默认（比如「用你不用您」）让位。
2. **用户这一行本来就说哪些专业词**：开发者工具里的「SSH 公钥」、基金 App 里的「净值」。这些是用户自己的词，换成白话反而认不出，不算第 1 类。判断办法：同行的产品界面上、这一行的文档里，用户自己也这么叫，才算用户的词；只在代码和接口文档里出现的不算。除此之外，代码里的名字和程序的说法在哪个产品里都不留，产品给程序员用也一样。
3. **东西在界面上叫什么、口气怎样**：页面上反复出现的对象和操作，现有文案怎么称呼（代码里往往是另一套叫法，不先查清就会把那一套写上界面）；称呼用「你」还是「您」，偏口语还是偏正式。用户能改的名字（昵称、自定义名称）从数据里取，不写死。

依据只用项目里本来就有的东西，不要求项目有哪份特定的文档：

- 现有的界面文案：挑十来条写得好的读。这是每个项目都有的依据。
- 有就读：规则文件（AGENTS.md、CLAUDE.md 这类）、设计或界面规范文档、多语言文案表、检查文案的测试。
- git 记录里专门改文案的提交：能看出哪些说法被特意改掉过。

都找不到依据的项（比如称呼、报错句式），才用 `<skill-dir>/references/conventions.md`，并注明用的是默认写法。

每条结论都附上依据的原文和出处（哪条现有文案、哪份文档里的哪句话）；找不到依据、自己推出来的，标「推断」。用户自己也分不清项目里哪些说法是本来就有的，不带出处的结论他没法核对。

用户群明显不同的几块（比如顾客用的 App 和商家后台）分开回答这三个问题，复述测试也按块分开派。

依据冲突时按这个顺序：用户这次的指令 > `decisions.md` 和项目成文的规范 > 项目现有文案里的多数写法 > `conventions.md`。`decisions.md` 和项目规范说的不一样时，不自己选，列进「拿不准」；没人可问时先按 `decisions.md` 做，在「拿不准」里写明。

项目里两种口气并存时，跟着这句话所在页面的写法走，不顺手统一，把并存的情况作为发现写进汇报。

## 记下用户拍板的事

用户在「拿不准」里选定了叫法、口气或别的写法后，记进项目根目录的 `.ux-writing/decisions.md`，下次会话直接用，不用再问一遍。

只记用户明确拍板的。自己归纳出来的产品结论不记，每次重新归纳：记下来就会被下次当成定论，归纳错了会一直沿用，也就没人再去核对。

每条一小段，格式固定：

```markdown
## 2026-03-01 订单页按钮改叫「退换货」（示意）
- 决定：订单详情页的「申请售后」改叫「退换货」，和点开后的页面标题一致
- 理由：用户点了「申请售后」，在打开的页面上找不到这个名字
- 针对：订单详情页按钮「退换货」
```

「针对」写这条决定落实之后界面上的位置和引号里的原文：改了名的写新名字，决定保留不改的写原来的字。它用来查这条还有没有用：写成改前的旧字，改完就搜不到了，每条落实了的决定都会被当成过时。每次读 `decisions.md` 时，拿每条「针对」里的原文在项目里搜一下：

- 搜不到了（页面删了、文字被别人改过）：在汇报「拿不准」的最后单列，写明这条决定和搜不到的情况，问用户要不要删，不自己删。
- 项目规范后来写了相反的话：按上一节说的冲突处理。

其他情况照用：用户有没有改主意，只有用户知道。

这个文件随这次改动一起交给用户提交，不放进 `.gitignore`：没提交的话，别的分支和工作树里看不到它。

## 怎么判断一句话

写和检查都用这一节。

### 先弄清它放在哪

对每一条，弄清五件事：

- **在哪**：哪个页面的哪个位置，用界面上的说法描述，不写文件路径。
- **是什么**：按钮、徽标、标题、提示条、确认框、空状态、悬停提示、权限说明、推送，还是成段的说明。
- **什么情况下出现**：用户刚做了什么，看到后能做什么。
- **旁边还有什么字**：同一组的其他选项、上方的标题、已经显示出来的信息。
- **会被读成什么**：放在这个位置、这个时刻，用户会把这句读成什么意思：「它」指谁，这个名字和旁边哪个名字说的是同一样东西，按钮点了以为会怎样。

下面的九类问题和「改之前那一关」，都拿最后一项读出来的意思去答，不只看字面。同一句话放在徽标里和放在确认框里，标准完全不同；不知道代码在什么情况下显示这句，改出来的意思就可能是错的。

写的时候有的项还定不下来（比如旁边放什么字还没设计），写「还没定」，交付前检查时补上。

### 九类问题

前五类多出在写的时候，第 6 类多出在回头改的时候，后三类两头都会出。用户说的「程序味」多落在第 1、2、3 类，「AI 味」多落在第 4、6、7 类。

第 1、2、3 类认出来就归必改，不因为「读得懂」降级：用户能猜懂一句程序的说法，不等于该让他去猜。产品给企业员工、后台操作人员或程序员用时也一样；只有用户自己行业里的词不算第 1 类。

写的时候用下面这张表就够；检查时，或者拿不准时，读 `<skill-dir>/references/checklist.md`，里面有每类的例子和「不算问题」的边界。

| 类 | 怎么认 |
|---|---|
| 1. 用了做的人才懂的词 | 用户嘴里会说这个词吗？界面上没解释过，他第一次看能懂吗？接口返回的错误原文、错误码显示到界面上也算（有意设计的除外，见交付前检查第 5 步） |
| 2. 指代悬空 | 把这句单独拿出来读，「这个」「那次」「它」指什么？ |
| 3. 讲程序在做什么 | 这句在回答「程序在干嘛」，还是「我怎么样了、我能干嘛」？ |
| 4. 替用户猜原因，或说了不真实的话 | 回到代码看：程序真的知道这个原因吗？这句承诺做得到吗？ |
| 5. 生造的口语 | 印在成熟产品的界面上会显得随便吗？去掉上下文别人听得懂吗？ |
| 6. 公文腔和改过头 | 是大家手机上天天见的说法吗？改后是不是更长、更绕、更像文件？ |
| 7. 塞太多、重复或空话 | 遮住这句，用户会少知道什么？ |
| 8. 不看放在哪 | 按钮、徽标放得下吗？报错、提示条、空状态给了下一步吗？ |
| 9. 同一个东西几种叫法 | 同一个东西在两处叫法不同时：用户会以为是两样东西吗？在一处看到这个名字，到另一处找得到吗？两样都不会，就不算 |

### 改之前那一关

动手改任何一条之前先问：**这是用户会读不懂、读错、被误导，还是只是我会换个写法？** 按这句放在那里会被读成什么来答，不只看字面。后者不改。确实属于第 1、2、3 类的，不算「换个写法」。多数文案本来就是好的；改得越多，用户要核对的越多，改错意思的机会也越多。法务、监管要求的固定文案只指出，不改。

### 改的时候守住的几点

- **意思不变**：原文说的是现象，就不要改成你从代码里读出来的原因。
- **同一个词别处也在用的**，要改就一起改，并列出连带改动。
- **一句话要覆盖好几种情况时**（比如几种失败共用一句报错），从代码里列出会走到这句的每一种情况，逐个代进去问：对这一种，这句是真话吗？给的下一步管用吗？示意：「暂时没法保存，过一会儿再试」同时用在「服务暂时连不上」和「这个账号没有保存权限」上，后一种等多久都不会好，用户会白等。
- **改兜底的时候**（比如把看不懂的报错统一换成一句通用的话），先找出会走到这里的、项目自己写好的人话报错，确认改完它们仍然原样显示。判断「是不是人话」的规则很容易把带英文名、带数字的中文报错也一起换掉：用户原来看到的是「还没填 API key」，知道去哪补，改完只看到「稍后再试」，可不补上 key，等多久都不会好。
- **改出来的新句子要再读一遍**：复述测试读的是改前的原文，改后的句子还没人以读者的身份读过。改完把改过的句子放回「先弄清它放在哪」重新过一遍，再做一次复述测试，只测这些句子；只改了标准词或标点的，和第一轮一样可以不复述。示意：在「设置 → 数据」页的导出那一行写「先到设置 →『数据』里处理」，用户本来就在这一页，等于原地打转。

## 写的时候

写功能时注意力在代码上，字是顺手带出来的。先把字单独拿出来，才有机会像读者那样看它们。

1. **动手写代码之前，先在回复里列出这次要新增或修改的界面文字。** 每条写清「先弄清它放在哪」的五件事，再加两样：照着哪一条现成文案写（同页面或相邻页面里的同类文字，比如同一种按钮、同一种报错）；拟写的文字。照着现成的写，叫法和句式自然和产品一致。
2. **按「怎么判断一句话」一节把清单过一遍**，有问题的先在清单里改掉。
3. **全新的概念没有现成文案可照时**，给它起的名字按「拿不准」的格式单独列出：有人可问就问，定下来记进 `decisions.md`；没人可问就先用一个容易撤回的默认（贴近用户的说法、不和已有叫法撞车），在汇报里写明。
4. **写完做一遍交付前检查。** 清单里的字写进代码时常会变样，还会多出写着写着才加的提示和报错，这一遍查的就是这些。新文字在对照表里「改前」填「（新增）」。

## 交付前检查

回头看文案有自己的坑：凭印象列出代码里没有的文案、把正常的词也改掉、把意思改错。下面的顺序就是冲着这些坑排的。

### 1. 从代码里取出文案

不凭记忆列，用脚本取：

```bash
python3 <skill-dir>/scripts/changed_copy.py --branch         # 当前分支自己的提交加上还没提交的改动，含未跟踪的新文件
python3 <skill-dir>/scripts/changed_copy.py                  # 只取还没提交的改动
python3 <skill-dir>/scripts/changed_copy.py --range A..B     # 两个提交之间
python3 <skill-dir>/scripts/changed_copy.py --all src/       # 这些路径下的全部文字，可给多个路径
```

`--branch` 自己找主干（依次看远程默认分支、main、master），主干叫别的名字时写成 `--branch 主干名`。

英文界面或中英混排的文案表加 `--ascii`；在别的目录跑加 `-C 目录`；要结构化输出加 `--json`。脚本扫常见的前端和移动端源码，以及 strings.xml、.strings、.xcstrings、.arb、.po、.properties 这类集中存放文案的文件；项目用了别的扩展名，用 `--ext .foo,.bar` 补上。输出带文件和行号，文案表带键名，改动模式下还列出同一处删掉的旧文字。

脚本默认跳过测试文件、依赖和构建目录。项目里还有别的用户看不到的整块路径（演示数据、样张页、评测、只给开发者看的页面），先打开里面几个文件，确认用户确实看不到，再用 `--exclude 路径,路径` 去掉（相对仓库根目录写，目录写到哪一层都行，也可写通配符），汇报里列出排除了哪些路径。脚本对一条都没去掉的路径会提醒，多半是路径写错了，改对再跑。

脚本只做提取，会多也会漏，取出来后自己过一遍：

- 去掉用户看不到的：日志、写给模型的提示词、测试数据、只在开发者模式里出现的内容。
- 补上取不到的：拼接出来的句子、接口返回后原样显示的文字、写在配置或数据里的文字。
- 「留意」一栏只是提醒多看一眼，其中「对照现有口气」只说明这里的口气可能和项目其他地方不同。命中的可能没问题，没命中的也可能有问题。

### 2. 每条回到现场

读每一条所在的代码，按「先弄清它放在哪」弄清五件事。

### 3. 对照九类问题

读 `<skill-dir>/references/checklist.md` 和 `<skill-dir>/references/conventions.md`。第 4、6、8、9 类要看代码和别的页面才能判断，由你自己答：程序是否真知道这个原因、改动是不是改过头、位置和宽度合不合适、两处叫法放在各自的位置会不会让人以为是两样东西。

### 4. 复述测试

写的人读自己的文字总觉得通顺，所以要找一个没看过代码的读者。读 `<skill-dir>/references/retell.md`，按里面的格式准备清单，连同其中给读者的说明原样交给一个子代理。复述说错了、或读不出意思的才算问题；说对了但标了「不顺」的，归入可改可不改。第 1、2、3、7 类主要靠这一步发现；第 9 类拿不准时，也看读者是不是把两个叫法读成了两样东西。读者对口气的感受只作参考。

派不了子代理时，自己按同样的输入做一遍，在汇报里注明「由写的人自查，可信度低」。这次只动了标准词（保存、取消、删除这类）或只改了标点时可以不做，汇报里写明跳过了。

### 5. 分级

第 3、4 步标出来的条目，先过「改之前那一关」，再分级：

- **必改**：用户会看不懂、理解错、被误导；第 1、2、3 类的问题，哪怕读得懂；说的和程序实际做的不一样；出了错不告诉用户能做什么；界面上显示了接口返回的错误原文或错误码（有意设计的除外）。直接改。
- **可改可不改**：读得懂，只是不够顺、口气可以更好、标点不统一（第 1、2、3 类不在这里）。默认不动，汇报里一句话说有多少条、什么类型。第 5、6、7 类看后果分：会让用户读错、被误导、或说了不真实的话的（比如带了对用户的评判），归必改；只是随便、啰嗦、多余的，归这里。`checklist.md` 例子里标的「该改」只说明它是个问题，归哪一级按这里分。
- **改名**：功能名、状态名、列名、分类名（比如失败原因的名称）这类用户已经认熟的叫法。不直接改，列进「拿不准」：改名会牵动别的页面、帮助文档和用户的习惯。这类叫法就算属于第 1、2、3 类，也按改名处理，不按必改直接改。

改的时候按「改的时候守住的几点」来。有两种情况，只改字改不好，要动几行代码：

- **话说得含糊，但代码手边就有能说具体的信息。** 有些提示要覆盖好几种情况，只好说得笼统，比如「上传失败」「操作失败」。先看显示这句话的那段代码手边有没有现成的数据能分清是哪种情况：接口返回的错误码、刚刷新回来的数据里这条记录的当前状态、用户刚选的文件或刚填的内容。有的话，按情况各写一句具体的话，用这些数据挑一句显示；分不清时仍显示原句。比如上传附件失败时一律显示「上传失败」，而代码里已经拿到了文件大小、也知道上限是 20MB，就在超过上限时显示「文件超过 20MB，请压缩后再上传」，其他情况仍是「上传失败，请重试」。要拿到这些信息得新发一次请求，或者得改按钮、改操作步骤才能说清时，不改代码，在汇报里写出建议。
- **界面上显示了接口返回的错误原文或错误码。** 原文是写给程序员看的，常是英文、带编号和字段名；错误码不管是数字还是 `PERMISSION_DENIED` 这类英文名，用户多半看不懂、用不上。项目自己的后端专门写给用户看的话（中文、说清了怎么办，比如「还没填 API key」）不算这里说的原文，照原样显示，换的只是英文报错、状态码、字段名这类写给程序员的东西。默认不显示：被查范围里的代码把它们显示给用户的，不管是直接显示，还是经过项目里共用的取错误文字函数原样带出来，都在被查范围的代码里换成自己写的话，说清发生了什么、能做什么：认识的错误码各写一句，不认识的用一句通用的报错。有意设计的展示照项目做法保留，但要有看得见的依据：项目规范或产品文档要求显示；用户这次指令要求；或者项目专门做了放它的地方，比如可复制的「错误码 / 参考编号」区域、排障用的折叠区（要把编号报给客服、银行或 IT 的产品常这样做）。保留的编号只能跟在人话后面，不能代替人话；项目做好的这类区域不删，也不改它显示什么，在汇报里写明它会露出原文，交给用户定。只是通用报错模板顺手拼上了错误码、没有别的依据的，不算有意设计：被查范围里用到它的地方换成不带码的说法。共用函数全项目都在用，改它会影响所有页面，不动它，在汇报里指出。

### 6. 改代码，然后汇报

改完：

- 改过的句子按「改的时候守住的几点」最后一条再读一遍、再复述一次。
- 项目的测试有时直接断言界面上的句子，跑一次和改动文字相关的测试，失败的照实写进汇报。
- **重新跑一次脚本**，按新的输出写对照表，保证每一行都对得上真实改动：

| 位置 | 改前 | 改后 | 原因 |
|---|---|---|---|
| 问诊页 · 发出消息后的状态（示意） | 消息已入队，等待对端响应 | 已发送，等待医生回复 | 「入队」「对端」是程序的说法，用户想知道的是在等谁 |

- 「位置」写界面上的位置；新写的文字「改前」填「（新增）」，让用户看到这次多了哪些字。
- 「原因」一句话说这句对用户哪里不好，不写「优化表达」这类空话。
- 只改了标点或空格的不进表，合成一句话说明。

汇报按下面的顺序写。要用户做决定的放在对照表前面：对照表常有几十行，放在后面的待定项容易被漏看。

1. **一句话结论**：按什么范围查的、改了多少处、在哪几个文件、有没有提交。再写「先弄清这个产品」的三条结论，每条带出处，推断的标「推断」，方便用户一眼看出方向对不对。
2. **拿不准**：起名、定叫法、涉及口气的多半在这里。每条写五项：
   - 在哪、什么时候看到；
   - 在那里会被读成什么；
   - 整句的改前和改后，候选不止一个时每个都写成整句；
   - 推荐哪个，一句理由；
   - 不改的代价。

   没人可问时先用的默认也列在这里，写明怎么撤回。`decisions.md` 里搜不到「针对」原文的条目单列在最后，不套这五项。
3. **对照表**：条目多时按页面分组，每组一个小标题。
4. **没验证的**：只读了代码、没在页面上看过的，如实说：会不会撑破按钮、会不会被截断，要看了页面才知道。没跑的测试也写在这里。
5. **过程信息**：项目里口气并存的情况；用 `--exclude` 排除了哪些路径；看了多少条、改了多少条、多少条属于可改可不改没动；复述标记了但没采纳的条目和原因。

## 范围大时分批

取出来超过一两百条时就分批，不管范围是整个项目、某个模块还是一串提交；整个项目几乎总会超过。一次看太多，读到后面已经记不清前面的，就会开始凭印象改。

怎么分：看脚本输出里条目在各个文件的分布，按界面入口分批：路由目录、功能目录各成一批，一个页面和它弹出的弹窗、提示放在同一批。同一屏上会一起出现的文字放在一批里，才判断得了语境和叫法。每批一两百条左右。要用 `--exclude` 排除哪些路径，开工前一次定好，每批都用同一套。

主会话自己做时，一批从取文案走到改完，再做下一批。中途不停下来等用户确认，拿不准的攒到最后一起交给用户。

交给子代理时，几批可以同时做。说明里写进：「先弄清这个产品」的结论、`decisions.md` 里已定的叫法、`checklist.md`、`conventions.md` 和项目规范文档的路径、要排除的路径、这一批的文件范围。并且要求子代理：

- 只改必改的，其余只交回，不改。
- 叫法和口气方面的问题不给推荐，交回原文、文件和行号，以及「先弄清它放在哪」的五件事：主会话没读过这些代码，要靠它们写「拿不准」；几个子代理各自推荐，会推荐出几套叫法。
- 复述测试：能派读者就自己派，改后的句子再派一轮；派不了时把按 `retell.md` 准备好的清单交回，由主会话统一派。
- 不跑项目的测试：几个子代理同时跑，慢，还会互相干扰。
- 交回的每一行带文件和行号。

收回后用脚本输出核对，对不上的整份退回重做。各批交回的叫法、口气问题，由主会话去重合并，统一给推荐；全部改完后，主会话跑一次和改动文字相关的测试，再按「改代码，然后汇报」写一份汇报。

## 退路

- **不是 git 仓库，或没有 python3**：脚本用不了。逐个读这次动过的文件，把界面文字抄成清单，每一条都要是代码里的原文。
- **文案来自后端、CMS 或配置平台**，不在仓库里：指出来，请用户给出原文和出现的位置；拿不到就在汇报里列为没查到的部分。
- **多语言文案表**：只改源语言，键名和占位符（`{count}`、`%s` 这类）原样保留；其他语言只指出需要跟着改，不动。

## 不做的事

- 不替用户定叫法和口气：会牵动别的页面和用户的习惯，给候选让用户定。
- 不改项目的规则文件和规范文档：那是项目的决定。觉得该写进去的，作为建议写在汇报里。用户拍板的事只记在 `.ux-writing/decisions.md`。
- 不提交：用户要先看对照表。
- 不保证文字放得下：要看了页面才知道，没看过就如实说。
