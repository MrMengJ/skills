# 全局记忆维护规范

全局记忆存放在 `~/.agents/memory/`，所有 agent 共用这一个目录。各工具看到的记忆索引由 `~/.agents/sync.sh` 生成，写在各自的全局规则文件里。

## 何时提议

- 用户纠正了你的协作方式，而且这个纠正和具体项目无关
- 踩了坑才发现的规律、不容易想到的事实
- 跨项目都成立的用户偏好、习惯、约束

判断标准：**换个项目还成立**。

## 何时不提议

- 跟某个具体项目的代码、决策、踩坑史强绑定 → 写进该项目自己的规则文件（项目根目录的 `AGENTS.md` / `CLAUDE.md`）或工具自带的项目级记忆
- 用户要整理给**他自己**看的知识（笔记、知识库、文档）→ 不属于记忆。记忆是给 agent 自己看的协作备忘
- 短小、任何时候都适用的行为规则 → 更适合写进公共规则 `~/.agents/AGENTS.md`，提议时说明这一点

## 提议的格式

在任务收尾时一次列出，每条包括：

1. 拟写的 description（一句话，主题 + 结论）
2. 为什么换个项目也成立
3. 公共还是本工具专属
4. 新建文件，还是补充到已有的哪个文件

**用户同意后再写入。** 修改、删除已有记忆同样要先提议、得到同意。

## 公共还是专属

先问：**换个 agent，这条还成立吗？**

| 情况 | 写法 |
|---|---|
| 所有 agent 都成立 | 公共记忆：`<类型>_<主题>.md`，不写 `applies_to` |
| 只对你这个工具成立 | 专属记忆：`<类型>_<主题>.<id>.md`，frontmatter 写 `applies_to: [<id>]` |
| 原则通用，具体做法各工具不同 | 拆开写：原则进公共文件，你的做法进你的专属文件，两个文件用同一个前缀 |

- 你的 id 写在全局规则文件开头的身份行里（「你当前的身份：…（记忆里 applies_to 用的 id 是 `xxx`）」）。所有合法的 id 见 `~/.agents/targets.txt` 第一列
- 写之前先看 `~/.agents/memory/` 里有没有同主题的文件，有就在原文件上补充，不要另起一个

## 文件格式

```markdown
---
name: <文件名去掉 .md，下划线换成连字符>
description: <主题 + 结论，一句话>
applies_to: [<id>]      # 只有专属记忆才写
metadata:
  type: feedback        # 协作反馈用 feedback；事实性参考用 reference
---

规则本身（一两句）。

**Why:** 为什么要这样做（一句）。

**How to apply:**
- 具体怎么做
```

文件命名：协作反馈用 `feedback_<主题>.md`，事实参考用 `reference_<主题>.md`。

## 写法要求

- **description 写「主题 + 结论」，不要只写主题。** 索引里每条记忆只显示一行 description，而且这一行一直在上下文里；写成结论，agent 不打开文件也能照着做。
  - 差：「git 合并冲突的处理原则」
  - 好：「git 合并冲突：锁文件、生成文件这类机械冲突自己解决；涉及业务逻辑的停下来交给用户」
- **正文只写规则、一句 Why、怎么做。** 不写项目名、日期、事情经过。例子只在能划清「什么算、什么不算」时才写，而且只写一句
- **不记会变的具体值**，比如模型版本号、目录里当前有哪些文件。只记档位、规律和去哪里查，需要时现查
- **专属文件和它的公共文件之间，不写互相指向的话**（「见公共文件」「本文件只写 xx 的做法」）。两者的关系由同一个文件名前缀和索引里挨着列出来表达
- description 的值里不要出现半角的「冒号 + 空格」（`: `），否则会被当成 YAML 语法；需要冒号时用全角「：」
- 和别的记忆相关时，用 `[[name]]` 链接

## 写完、改完、删完之后

1. 运行 `~/.agents/sync.sh`，重新生成各工具的索引
2. 运行 `~/.agents/sync.sh --check`，确认没有报问题；有问题先修好
3. 告诉用户：新的索引要等**下次新开会话**才会生效
4. `~/.agents/` 是 git 仓库。**不要自己提交**，提醒用户：这次改动还没提交，列出 `git -C ~/.agents status --short` 的结果，由用户决定是否提交、是否推送
